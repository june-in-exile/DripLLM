讓沒有計費基礎設施的小型推論供應商,能對機器客戶按秒收費 —— 持續付費才有推論,停付就被剪線。

問題

想收費就得先建帳號系統、金流、發票、授信催收、退款爭議、防詐。 這套成本與客戶數無關,是固定門檻 —— 大公司攤得掉,一個人跑自架模型的攤不掉。

走這條路,供應商只需要一個收款地址加一段 middleware。 成本結構也對得上:小型自架供應商的真實成本是 GPU 被佔用的時間,不是 token 數。

一個硬邊界

門檻沒有消失,是換邊了:每個客戶都得有一個裝了 USDC 的錢包。 對人類客戶這是死穴;對 agent 不是 —— agent 本來就是被程式佈建出來的。

串流計費 誰承擔風險
一般 request/response 用 per-request x402 就夠了。沒有現成答案的是跑好幾分鐘的串流。
整段預收 買方承擔對手方風險 —— 付了錢對方跑掉
先給後收 賣方承擔授信風險 —— 送完了對方不付
切成一格一格 任一方對另一方的曝險都不超過一格

gas 厘級 多次補款不被手續費吃垮

一次 tick 的資料流
1POST /tick 沒帶付款 → server 回 HTTP 402 附價格與收款資產
2agent 簽一筆 USDC 付款,塞進 X-PAYMENT header 重送
3facilitator 驗證簽章,並在 Fuji 上結算
4onAfterSettle 建立 session,回 { sessionId, accepted }
5agent 用該 sessionId 開 GET /stream,token 開始流動
6餘額低於門檻時自動再送一筆 tick,把 paidUntil 往後延
✂逾期又超過寬限 → server 送 event: cut,主動關閉連線
三個端點,只有一個收費
端點x402職責
POST /tick收費付一筆 → 建立或延長 session
GET /stream免費SSE,session 活著就吐 token
GET /health免費啟動檢查與 demo 腳本

/stream 免費不構成漏洞:session 只有付過錢才存在。 這讓 x402 middleware 留在它天生擅長的 per-request 位置,SSE 那條完全不碰付款邏輯。

為什麼要長連線:若每個 tick 都是獨立 request,「斷流」不過是 agent 自己 break 迴圈, server 從頭到尾沒行使任何權力。長連線下 agent 還連著、還想要,線卻被剪了。

03 參數與 Demo 觀察重點

有意義的量只有一個:曝險窗口

參數值說明
CREDIT_PER_TICK_MS25000一筆付款買到的串流時間(實測 settle 7.4–10.6s)
TOPUP_THRESHOLD_MS15000餘額低於此值即補款
GRACE_MS2000逾期後才剪線的寬限
PRICE_PER_TICK_ATOMIC10000.001 USDC
MAX_SPEND_ATOMIC500000.05 USDC,約 50 個 tick

agent 是在餘額將盡時補款,不是固定間隔付款 —— 否則網路與結算延遲會讓餘額逐 tick 向下漂移, 幾個 tick 後就自行斷流。所有參數經 src/config.ts 以 zod 驗證後注入,無硬編碼。

第一次 Ctrl-C:agent 停止付款,但保持連線、繼續讀 stream。約 17～35 秒後 server 主動剪線, 第二次 Ctrl-C 才真正退出。第一次不斷線是整個 demo 成立的關鍵 —— agent 仍連著、仍在等待,線是 server 剪的。
