Lets small inference providers with no billing infrastructure charge machine customers by the second: keep paying and the inference keeps flowing; stop paying and the line gets cut.

The problem

Charging money first means building accounts, payment integration, invoicing, credit and collections, refund disputes, fraud prevention. That cost doesn't scale with the number of customers; it's a fixed barrier to entry. Big companies can amortize it; one person running a self-hosted model can't.

With this approach, a provider needs only a receiving address and a piece of middleware. The cost structure lines up too: for a small self-hosted provider, the real cost is the time the GPU is occupied, not the token count.

A hard boundary

The barrier doesn't disappear; it changes sides: every customer needs a wallet holding USDC. For human customers that's a dealbreaker; for agents it isn't, since agents are provisioned by code in the first place.

Billing a stream Who bears the risk
For ordinary request/response, per-request x402 is enough. What has no off-the-shelf answer is a stream that runs for several minutes.
Prepay the whole thing The buyer bears counterparty risk: pays, and the seller disappears
Serve first, bill later The seller bears credit risk: delivers, and the buyer never pays
Slice it into ticks Neither side's exposure to the other ever exceeds one tick

Data flow of one tick
1POST /tick without payment → HTTP 402, with payment requirements in the PAYMENT-REQUIRED header
2First tick: sign an ERC-3009 deposit + the first voucher, put them in PAYMENT-SIGNATURE and resend; the facilitator submits on-chain
3Every tick after: sign only an off-chain voucher (cap = consumed + one tick); round trip measured 7–16ms
4onAfterSettle creates or extends the session and returns { sessionId, accepted }
5The agent uses that sessionId to open GET /stream, and tokens start flowing
6When event: credit shows < 300ms remaining, send another /tick to extend paidUntil
✂Overdue and past the grace period → the server sends event: cut and actively closes the connection
Endpoints: only /tick is paid
Endpointx402Responsibility
POST /tickPaidPay for a tick → create or extend the session
GET /streamFreeSSE; emits tokens while the session is alive
GET /healthFreeReturns { ok, sessions }, for tests

/stream being free isn't a loophole: a session only exists once it has been paid for. This keeps the x402 middleware in the per-request position it's naturally good at, and the SSE path never touches payment logic.

Why a long-lived connection: if every tick were an independent request, "cutting the stream" would just be the agent breaking out of its own loop, and the server would never exercise any power at all. With a long-lived connection, the agent is still connected and still wants more, yet the line gets cut.

Only one quantity matters: the exposure window

The agent tops up when its credit is about to run out, not on a fixed interval. Otherwise network and settlement latency would make the credit drift downward tick by tick, and after a few ticks the stream would cut itself off. All parameters are validated with zod by src/config.ts before injection; nothing is hard-coded.

First Ctrl-C: the agent stops paying but stays connected and keeps reading the stream. After the remaining credit + the 250ms grace period + one 100ms sweep, the server cuts the line; on receiving event: cut, the agent refunds its deposit and exits on its own. The first Ctrl-C not disconnecting is what makes the whole demo work: it's the server that cuts the line.
